# Lead Qualification CRM — multi-client template

One codebase, one profile file per client. **Never fork the code for a client** — add `clients/<id>.ts` and deploy with `CLIENT_ID=<id>`.

## Onboarding a new client (the whole job)

1. **Collect answers** using `CLIENT_INTAKE.md`. Ask the user only for what's missing and required: business name, tagline, description, owner label, brand colour, booking link, at least one service, form title/intro/main question/example, challenge noun. Everything else has defaults.
2. **Create the profile:** copy `clients/_template.ts` → `clients/<id>.ts` (`id` = lowercase-dashed business name, must equal file name). Fill every `REPLACE`. Map services onto slots:
   - `one_to_one_coaching` = individual / 1:1 offer
   - `group_program` = group, cohort, course, membership
   - `corporate_training` = B2B / team / company (scores +points when org or team size given)
   - `speaking` = events, talks, workshops
   Disable unused slots (`enabled: false`). Slot ids are internal; only labels are shown.
3. **Brand colour too light?** Validation needs contrast ≥ 4.5 with white. Darken the same hue until it passes and tell the user.
4. **Switch + validate:** `npm run use-client -- <id>` (fails with a clear list if anything is wrong; keeps the previous client active on failure).
5. **Verify:** `npm test && npm run build`, then `npm run dev` and look at `/inquire` and `/` — check name, colour, services, wording.
6. **Switch back** if another client should stay active locally: `npm run use-client -- george-stern`. The active client in git doesn't matter for deploys — Vercel builds whatever `CLIENT_ID` says.
7. **Deploy** (README §3): new Vercel project from this repo, env vars `CLIENT_ID=<id>`, `DATABASE_URL` (client's own Supabase), `CRM_OPERATORS` + `SESSION_SECRET` (`npm run hash-password -- <email> --with-secret`, the client types the password), optional `EMAIL_*`, `OPENROUTER_API_KEY`. Each client gets its own database — never share one.

## What lives where
- `clients/<id>.ts` — everything client-specific (schema + docs in `src/config/schema.ts`).
- `src/config/active-client.ts` — generated by `scripts/use-client.mjs`; imports exactly one client so no other client's data ships in the bundle. Don't hand-edit.
- Settings page — the client can later change name, colour, tagline, booking link, offers, scoring and templates at runtime; those are stored in their database and override the profile defaults.
- Brand colour: Tailwind `brand` / `brand-hover` colours (`bg-brand`, `text-brand`, `ring-brand/20`). Never hard-code hex colours in components.
- Client-facing text: read from `client` (`@/config/client`) — never hard-code a business name, service name or niche wording in `src/`.

## Limits of the template (tell the user when a client needs these)
- Max 4 services; the form always asks role, organisation, team size, service, timing, and one free-text question. A client needing different form fields (e.g. budget, location) or a non-service business (e.g. clinic bookings) needs code changes, not just a profile.
- Fictional demo leads (local dev / `SEED_DEMO_DATA`) are leadership-coaching flavoured. Real deployments start empty.
- The contradiction heuristics in `src/lib/scoring.ts` assume coaching/speaking language.

## Checks before saying done
`npm test` (includes `tests/client-config.test.ts`, which validates every client file) and `npm run build` must both pass after the last edit.
